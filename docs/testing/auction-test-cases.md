# オークションサービス テスト仕様書

- 文書状態: レビュー中。
- 対象: 認証、出品、閲覧、入札、終了・落札、権限、障害復旧。
- 本書は期待する動作を定義する。実行結果や実装済みであることを示すものではない。

## 1. 前提と実行方法

テスト専用環境・架空データを使用する。出品者S、購入者A・B、運営者M、ゲストGを用意し、各ケースは独立したデータで実施する。特記がない場合、出品は公開・開催中、会員は利用可能、即決価格なし、自動延長なしとする。金額は整数JPY、保存・API日時はUTC、画面表示はJSTとする。

時間境界はDB判定時刻を制御して確認する。競合テストは独立したDB接続とトランザクションを使い、バリア等で処理順を制御する。単なる逐次実行やブラウザの連打で代替しない。SQLite3とPostgreSQLのロックの差を考慮し、PostgreSQL移行時には同じ競合ケースを同DBで実行する。

各実行でケースID、対象コミット、環境・DB、日時、担当者、実際の結果、証跡、判定、関連不具合を記録する。判定は「合格／不合格／未実行／保留」。機能が用意されていないケースを合格扱いにしない。APIのHTTPステータス・フィールドが未決の場合は業務結果だけを検証し、その未決項目の確認は保留として記録する。

仕様の根拠は [業務ルール](../product/auction-rules.md)、[入札・終了処理](../architecture/auction-bid-transaction.md)、[API仕様](../api/openapi.md)、[認証設計](../architecture/auth-001-google-login-design.md)、[要求仕様](../product/auction-site-spec.md)。出品の数値上限と画像省略は開発段階の仮条件とし、正式化・変更時にケースを更新する。

## 3. 入札額と自動入札

各ケースでは別の冪等性キーを使用する。AUTO-01〜04は開始価格100円でAが最高入札額700円を受け付けた状態を起点とし、各ケースを独立させる。

| ID | 前提・入力・操作 | 期待結果 | 検証層 |
|---|---|---|---|
| BID-01 | 開始価格100円、入札なし。Aが100円／99円を入札（各独立） | 100円は受付、現在価格100円。99円は拒否 | 単体・API統合 |
| BID-02 | Sが自分の出品へ入札 | 拒否され、Bidなし | API統合 |
| BID-03 | 下書き・停止・キャンセル・終了の各状態へ入札 | すべて拒否され、価格・履歴・Orderに変更なし | API統合 |
| BID-04 | 0・負数・小数・文字列・真偽値・1,000万1円を金額として送信（各独立） | 正の整数JPYとして拒否、暗黙変換で受け付けない | API統合 |
| BID-05 | 開始価格100円、入札なし、即決なし。Aが1,000万円を入札 | 上限値として受付。現在価格は100円 | API統合 |
| BID-06 | 現在価格1,000円、A以外のBが1,099・1,100・1,101円を入札（各独立） | 1,099円は拒否。1,100・1,101円は受付 | 単体・API統合 |
| AUTO-01 | Bが500円を入札 | 受付成功、Aが最高額入札者のまま、現在価格510円。Bの結果はoutbid | 単体・API統合 |
| AUTO-02 | Bが715円を入札 | Bが最高額入札者、現在価格710円。結果はleading | 単体・API統合 |
| AUTO-03 | Bが700円を入札 | 先に受付確定したAが優先、現在価格700円。Bはoutbid | 単体・API統合 |
| AUTO-04 | Aが900円へ増額 | Aが最高額入札者のまま、現在価格100円。他の会員に900円を返さない | 単体・API統合 |

## 4. 時刻・延長・終了

Tは保存済み終了日時。延長ケースでは自動延長あり、価格が上がる有効な入札を使う（特記を除く）。時刻のεはテスト対象DBが扱う最小精度以上とする。

| ID | 前提・操作 | 期待結果 | 検証層 |
|---|---|---|---|
| TIME-01 | 判定時刻をT−ε／T／T＋εとして入札（各独立） | T−εのみ受付。T以降は拒否。終了ジョブが遅れていても同じ | 境界統合 |
| TIME-02 | Tより前に送信し、ロック待ち後のDB判定時刻をT以降にする | 送信時刻にかかわらず拒否 | 競合統合 |
| EXT-01 | T−5分−1秒に入札 | 受付するが延長しない | 境界統合 |
| EXT-02 | T−5分ちょうど／T−εに入札（各独立） | 価格上昇とともに終了日時がT＋5分になる | 境界統合 |
| EXT-03 | 自動延長なしでT−1分に価格が上がる入札 | 終了日時はTのまま | API統合 |
| EXT-04 | 自動延長あり、T−1分に最高額入札者が増額 | 現在価格が変わらず、終了日時もTのまま | API統合 |
| EXT-05 | 延長後の終了日時に対して再び延長条件を満たす | さらに5分延長。古い終了日時で落札確定しない | 競合統合 |
| END-01 | 入札なしでTに終了処理 | ended、落札者なし、Orderなし | 統合 |
| END-02 | Aが700円、Bが500円の入札後に通常終了 | Aが510円で落札。Orderは1件、awaiting_payment、商品・配送条件をスナップショット保存 | 統合 |
| END-03 | 即決価格3,000円に3,000／3,500円を入札（各独立） | 即終了、本人が3,000円で落札。won、ended、Orderは1件 | API統合 |
| END-04 | Sが入札あり／なしの出品を終了時刻前に早期終了（各独立） | 入札ありは現在価格で最高額入札者のOrderを1件作成。なしは落札者・Orderなし | 統合 |
| END-05 | 同じ終了処理を逐次・並行に再実行 | 終了結果・Order・通知イベントを重複作成しない | 競合統合 |
| END-06 | Mが停止後、Tより前／T以降に終了処理（各独立） | 前者は停止維持、後者はcancelled。いずれもOrderなし、入札履歴は維持 | 統合 |

## 5. 競合・冪等性・障害

| ID | 前提・操作 | 期待結果 | 検証層 |
|---|---|---|---|
| CON-01 | A・Bが同じオークションへ異なるキーで並行入札。両ロック順を試す | 後続は先行確定後の最低額で再検証。受付順・価格・最高額入札者が直列実行結果と一致 | 競合統合 |
| CON-02 | 入札と取り下げ／編集／運営停止を競合（各組合せ・両ロック順） | 入札が先なら入札後編集・取り下げを拒否。取り下げ・停止が先なら入札拒否。編集先行なら変更後条件で再検証 | 競合統合 |
| CON-03 | 通常終了と入札、延長と終了を競合（各組合せ・両ロック順） | ロック取得後のDB時刻と最新終了日時で処理。終了後のBidなし、Order最大1件 | 競合統合 |
| CON-04 | 即決同士／即決と通常入札／早期終了と入札を競合（各組合せ・両ロック順） | 確定順に整合し、終了後のBidなし、落札者・落札価格が一意、Order最大1件 | 競合統合 |
| IDEM-01 | 同一会員・対象・キー・本文を逐次／並行送信 | 初回と同じHTTPステータス・本文。BidとOrderを重複作成しない | API・競合統合 |
| IDEM-02 | 同じキーで金額を変更して再送 | IDEMPOTENCY_KEY_REUSED、元の受付結果・履歴を維持 | API統合 |
| IDEM-03 | コミット後に応答を失わせ、同じキー・本文で再送 | 保存済み結果を返し、追加のBid・注文なし | 障害統合 |
| IDEM-04 | 最低額未満の確定した拒否を保存後、価格・状態が変わってから同じキーで再送 | 初回の拒否結果を返し、新規入札として評価し直さない | 統合 |
| IDEM-05 | leading受付後にBが上回り、Aが元のキーで再送 | 初回のleadingを返す。最新取得ではBが最高額入札者と分かる | API統合 |
| FAIL-01 | Bid・価格・冪等性結果・Outboxの各保存段階で失敗（各独立） | 全体ロールバック、部分確定なし。一時障害後は同じキーで再試行可能 | 障害統合 |
| FAIL-02 | 即決または通常終了のOrder保存・コミットで失敗（各独立） | 終了状態とOrderを部分確定しない。再実行で正しい注文を最大1件作成 | 障害統合 |
| FAIL-03 | 通知の送信先を失敗させ、送信処理を再実行 | Bid・落札・Orderを巻き戻さない。同一イベントの再送を管理し、ドメイン処理を重複実行しない | 障害統合 |

## 7. 合否とカバレッジ

入札・終了・権限・競合・原子性の不合格を残したまま対象機能を完了としない。各表の複数入力・組合せはサブケースとして実行結果を個別記録する。金額境界は単体とAPI、競合・冪等性はDB統合、主要フローはE2Eで確認し、画面テストだけでDB整合性を保証しない。

認証の署名・issuer・audience・nonce等のケースは認証設計のテスト表を併用する。画像検査、管理API、通知配信、運用復旧については、詳細仕様の確定に合わせてケースを補完する。実行コマンドは [バックエンド手順](../runbooks/local-backend.md) を参照する。

## 8. 仕様確認が必要な項目

次の項目は期待結果を独断で確定せず、[未決事項](../product/open-questions.md)・各機能の仕様で合意後にケースを追加する。

| 項目 | ケース化するために必要な定義 |
|---|---|
| 終了日時の1時間単位 | 公開時刻からの経過時間単位か、時刻の正時指定か。丸め・タイムゾーンの扱い |
| 最高額入札者の再入札 | 既存の最高入札額以下を指定したときの拒否コード・入力条件 |
| 検索・並び替え | 採用フィルター、同順位の順序、ページ境界、空結果 |
| 入札履歴 | 認証要否、匿名化、件数・表示順・ページング |
| 手数料・税 | 提案の合意状態、適用率・端数・表示・請求方法 |
| 画像 | 形式・枚数・サイズ、メタデータ除去、保存と削除 |
| 取引・評価 | 支払期限、配送、受取、キャンセル・返金・紛争・評価の権限と期限 |
| 通知・通報・退会 | 対象イベント・再送間隔、審査条件、退会制約とデータ保持 |
| レート制限・性能・復旧 | 制限値、負荷条件、応答目標、バックアップ保持・復旧目標と実行手順 |

これらの保留を、現在定義済みの入札・終了ケースの合格で代替しない。
