# セキュリティ・プライバシー方針

## 現在のプロトタイプ

- 静的HTML/CSS/JavaScriptで、認証・サーバーAPI・アプリDBを持たない。ログインフォームは案内のみで、メールアドレスやパスワードを保存しない。
- 出品、ウォッチ、デモ入札履歴は同一オリジンのブラウザ `localStorage` に保存される。利用者が開発者ツールから改変でき、共有・信頼性・機密性を保証しない。
- 入力表示時はHTMLエスケープを行う。画像URLはHTTPSのみ受け付けるが、許可ホストの制御・画像実体検査・マルウェア検査・EXIF除去は実装されていない。
- 外部フォントをGoogle Fontsから読み込む。プライバシー要件やネットワーク制約がある配布では、外部アクセスを評価して自己ホスト等を検討する。
- 実際の個人情報、秘密情報、決済情報、本番出品を入力しない。デモ内のサンプル商品・出品者は架空。

## 本番実装の必須管理策

### 認証・認可

- 実績のある認証基盤を選定し、独自のパスワード暗号・セッション方式を作らない。
- メール確認、アカウント状態、セッション失効、パスワード再設定、重要操作の再認証を設計する。
- 更新APIごとに認証、ロール、リソース所有者をサーバー側で検証する。一般ユーザーは出品者と購入者の両方になれる。
- Cookie認証ならSecure、HttpOnly、適切なSameSite、CSRF対策を構成する。CORSは許可元を限定する。

### 入力・Web攻撃

- すべての入力をサーバー側でスキーマ検証し、SQLインジェクション、XSS、CSRF、SSRF、IDOR、オープンリダイレクトを防ぐ。
- 文字数、配列長、整数範囲、リクエスト本文サイズ、ページサイズを制限する。
- 認証、出品、入札、通報、パスワード回復を用途に応じてレート制限する。エラー詳細から内部状態を漏らさない。
- セキュリティヘッダー、TLS、依存更新、秘密情報の保管とローテーションを運用に含める。

### 入札・取引の整合性

- 入札受付時に認可、所有者、状態、時刻、金額をトランザクション内で再確認する。
- 同時入札を直列化し、冪等性キーを保存・検証する。入札履歴は監査可能な追記型とする。
- 終了と落札者・注文確定を原子的かつ再実行可能にし、重複注文を防ぐ。
- クライアントからの決済成功申告を信用しない。将来決済を導入する際は署名済みWebhook、冪等性、重複イベント、返金照合を設計する。

### 画像・ログ

- 画像は許可形式、実際のMIME/デコード結果、ファイルサイズ、個数を検証し、危険なSVG等の扱いを定義する。
- 画像メタデータの位置情報除去、保存先のアクセス制御、署名付きアップロード/ダウンロード、有害コンテンツ審査を検討する。
- ログにパスワード、認証トークン、決済情報、不要な個人情報を記録しない。管理操作と重要状態変更は監査記録を残す。
- ログの閲覧権限、保持期間、削除、アラート、インシデント時の保全を決める。

### 個人情報・運用

- 収集目的、最小化、保存期間、削除請求、アクセス制御、委託先、バックアップ内データの扱いをプライバシー文書と運用手順に定める。
- stagingとproductionを分離し、productionデータを開発環境にコピーしない。バックアップは暗号化し、復元権限を制限する。
- 不自然な入札、吊り上げ、複数アカウント悪用を調査できる記録を、プライバシー配慮と保持方針の範囲で設計する。
- 日本向け規約、プライバシーポリシー、特定商取引関連表示、古物営業・資金移動等の論点を事業モデルに応じ専門家と確認する。

## 本番公開の制約

決済事業者、KYC条件、返金・紛争対応、法務・運用の承認が完了するまで本番資金移動を有効にしない。現プロトタイプはそれらの統制を備えていない。
