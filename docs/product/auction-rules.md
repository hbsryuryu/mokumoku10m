# オークション業務ルール

- 状態: 初期ルール案（未決事項を含む）
- 正式な実装: なし。現行デモの一部はクライアント内のみで動作する。

## 用語

- 開始価格: 出品者が設定する最初の入札可能価格。
- 現在価格: 受け付け済み入札の最高額。入札がなければ開始価格を表示上の基準とする。
- 最低入札額: 現在価格に最低入札増分を加えた金額。初回入札では開始価格以上。
- 受付時刻: サーバーが入札を検証・確定した時刻。ブラウザ時計は正式な判定に使わない。

## 将来の基本状態案

- 出品: `draft -> published -> ended`。審査・運用時に `suspended`、出品者操作等で `cancelled` が必要となる可能性がある。
- オークション: `scheduled -> active -> ended`。例外として `cancelled`。
- 取引: `awaiting_payment -> paid -> shipped -> delivered -> completed`。`cancelled` / `disputed` / `refunded` の許可条件は未決。

状態変更は許可された遷移だけを受け付け、管理操作や重要な変更は監査対象にする。具体的なキャンセル権限と返金条件は別途決定する。

## 入札成立条件案

1. 認証済みで、利用停止中ではない。
2. 対象出品が公開中で、オークションが開催中である。
3. 入札者が出品者本人ではない。
4. サーバーが判定した受付時刻が終了時刻より前である。
5. 金額が正の整数JPYで、設定済み上限以下である。
6. 初回は開始価格以上、以降は受付済み最高価格＋最低増分以上である。
7. 同時入札はDBロック等で直列化し、先に確定した状態を基準に後続入札を再検証する。
8. 同一冪等性キーの再送は同一結果を返し、履歴や価格を二重に更新しない。

入札履歴は通常削除・上書きしない。個人情報の保持・開示・削除の扱いはプライバシー設計で別途定義する。

## 終了と落札案

- 終了時刻後は入札を受け付けない。ジョブ実行時刻だけに依存せず、APIと終了処理の双方でサーバー時刻・DB状態を確認する。
- 終了処理は再実行可能にし、終了状態、最高入札者、取引作成を原子的かつ一度だけ確定する。
- 入札なし終了と落札あり終了を区別する。
- 通知送信失敗によって入札・落札確定を巻き戻さない。必要に応じてOutbox等で再送可能にする。
- 延長の有無、終了直前の入札受付境界、同額入札の優先順位は未決。

## 取引・決済案

落札時に購入者、出品者、落札価格、商品タイトル・説明・配送条件のスナップショットを持つ注文を作成する。注文状態、支払期限、キャンセル、返金、配送事故の手順は事業・決済設計を経て決める。決済機微情報をアプリDBに保存せず、決済成功は検証済みWebhook等のサーバー情報で確定する。

**この文書は決済を許可するものではない。** AGENTS.mdに従い、決済事業者・本人確認・返金・紛争・法務の運用準備が整うまで、本番の資金移動を伴う取引を公開しない。

## 未決決定の記録先

手数料・税、KYC条件、禁止商品、年齢制限、キャンセル・返品、同額入札、最低増分表、終了延長、決済・配送事業者は責任者を含むADRで決定する。決定前は利用者に約束する確定仕様として実装しない。
