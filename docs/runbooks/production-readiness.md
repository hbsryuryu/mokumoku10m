# 本番公開準備チェックリスト

このチェックリストが完了するまで、本番ユーザーから出品・入札を受け付けず、実際の決済を有効にしない。

## 事業・仕様

- [ ] 事業責任者、運用責任者、問い合わせ窓口、インシデント対応責任者を決める。
- [ ] 手数料・税、キャンセル・返品・返金・未払い・配送事故をADRと利用者向け規約に記録する。
- [ ] 禁止商品、年齢制限、出品停止、通報審査、異議申立ての基準と担当を定める。
- [ ] 終了延長、同額入札、最低入札増分、終了境界、落札不成立を決めてUI/API/テストへ反映する。
- [ ] 本人確認が必要な条件とアカウント制限を決める。
- [ ] 日本向け法令・表示要件を事業モデルに即して専門家に確認する。

## アプリケーション・データ

- [ ] 本番スタック、認証、DB、画像保管、メール、ホスティングを採用ADRで確定する。
- [ ] 認証、メール確認、パスワード回復、セッション失効、所有者認可を実装する。
- [ ] DBスキーマと移行手順、既存データへの影響、復旧方法をレビューする。
- [ ] 金額を整数JPY、日時をUTCで保存し、UIのJST表示と境界を検証する。
- [ ] 出品入力と画像の実体・サイズ・数・メタデータを検査する。
- [ ] 入札トランザクション、競合直列化、冪等性、自己入札禁止、同時入札統合テストを通す。
- [ ] 終了、入札との競合、入札なし終了、重複しない注文作成、ジョブ再実行を統合テストする。
- [ ] 通知失敗が取引状態を巻き戻さず、再送・重複排除できる。
- [ ] 通報、管理操作権限、監査ログ、ユーザー停止を実装する。
- [ ] 認証情報や決済機微情報をログ・DBに不用意に保存しない。

## 決済ゲート（決済導入時）

- [ ] 決済事業者と契約、本人確認、入出金、返金、紛争対応を確定する。
- [ ] テスト環境で支払い成功・失敗・重複Webhook・署名不正・返金を検証する。
- [ ] クライアント自己申告で決済済みにせず、Webhook署名検証と冪等処理を行う。
- [ ] カード情報等の決済機微情報をアプリDBに保存しない。
- [ ] 本番資金移動の有効化承認、緊急停止手順、問い合わせ体制を用意する。

## 運用・公開

- [ ] stagingとproduction、秘密情報、権限を分離する。
- [ ] 可用性・遅延・入札失敗・ジョブ滞留・メール失敗・不正兆候の監視と通知を設定する。
- [ ] バックアップの保持・暗号化・権限・復元試験と復旧目標を定める。
- [ ] レート制限、脆弱性確認、依存更新、セキュリティインシデント手順を整える。
- [ ] プライバシーポリシー、利用規約、保存期間、削除請求、委託先情報を整える。
- [ ] E2Eで登録から出品、検索、入札、終了、落札後取引まで通す（決済はテスト環境）。
- [ ] 公開判定会議で未解決リスク、監視、サポート、ロールバックを承認する。

## ロールバック時

アプリのロールバックで入札・注文データを削除・書き換えない。DB変更は事前レビューした復旧手順に従い、必要時は新規入札受付を安全に停止してから対応する。決済が導入された場合は、アプリ停止と資金状態の照合・返金判断を別々に行い、担当者へエスカレーションする。
