# 入札 API（BID-001）

- 状態: 実装済み（`apps/api/app/bids/`）
- 仕様（入出力・受け入れ条件）: [API 仕様書](openapi.md)「入札成功レスポンス（BID-001）」。この文書は、仕様書に書かれていない実装上の決め事をまとめる。
- ルール: [ADR-0007](../adr/0007-align-with-yahoo-auctions.md)（入札単位・自動入札・自動延長・即決）、手順: [トランザクション設計](../architecture/auction-bid-transaction.md)、テスト: [テスト仕様](../testing/auction-test-cases.md)
- 試し方: `docker compose up` → http://localhost:8000/docs で、出品者（例: `seller1`）が出品・公開し、別の名前（例: `buyerA`）でログインして入札する

## リクエスト

```http
POST /api/v1/listings/{listingId}/bids
Idempotency-Key: 7f3c9a1e-...（必須）
Content-Type: application/json

{ "amountYen": 2500 }
```

| 項目 | ルール |
|---|---|
| `amountYen` | **最高入札額**（この金額まで自動で競る）。1以上の整数。`"100"`・`1.5`・`true` などは変換せずに 422（テスト仕様 BID-04） |
| `Idempotency-Key` | 必須。英数字・`-`・`_` で1〜64文字（UUID など）。ないと 422 |

## 応答とエラー

成功は `201`（本文は仕様書のとおり。`result` は `leading` / `outbid` / `won`）。応答には `Cache-Control: no-store` を付ける（本人の最高入札額を含むため）。

| HTTP | `code` | いつ |
|---|---|---|
| 401 | `UNAUTHENTICATED` | 未ログイン、または利用停止中（ログイン中に停止された会員も未ログイン扱い） |
| 403 | `SELLER_CANNOT_BID` | 自分の出品への入札 |
| 404 | `LISTING_NOT_FOUND` | 出品がない、または下書き・取り下げなどで見えない |
| 409 | `AUCTION_NOT_ACTIVE` | 開催中でない（終了・運営停止）、または終了時刻ちょうど・以降 |
| 409 | `BID_TOO_LOW` | 最低入札額に足りない。`details` に `minimumBidYen` と `currentPriceYen` |
| 409 | `IDEMPOTENCY_KEY_REUSED` | 同じキーを別の金額で使った |
| 422 | `BID_LIMIT_EXCEEDED` | 1,000万円を超える。`details.maximumBidYen` |
| 422 | `VALIDATION_ERROR` | 金額の型・範囲、`Idempotency-Key` の形式 |

HTTP ステータスは仕様書で決まっていなかったため、「状態によって結果が変わるもの」は 409、「入力そのものの誤り」は 422 とした。

## 実装で決めたこと

| 項目 | 決めたこと | 理由 |
|---|---|---|
| 価格の計算 | `app/bids/pricing.py` の純粋な関数（DB を使わない）。入札者ごとに最も高い最高入札額を使い、自分の過去の入札は競争相手に数えない（AUTO-05） | 境界値を単体テストで確かめやすい |
| 最高額入札者の再入札 | 「最高入札額の引き上げ」として扱う。最低額は「今の自分の最高入札額＋1円」と「現在の価格＋入札単位」の大きいほう | ADR-0007「下げる操作は MVP では提供しない」 |
| 集計列 | `auctions.current_price`・`highest_bidder_id`・`bid_count` を持ち、入札と同じトランザクションで、全入札から計算し直して更新する | 一覧の価格順・入札数順の並び替えのため（トランザクション設計 11章の未決事項を「保持する」に決定） |
| 自動延長の「価格が上がった」 | 入札前に入札があり、入札後の現在の価格が入札前より高いとき。**最初の入札**（現在の価格は開始価格のまま）と、最高額入札者の引き上げでは延長しない | ADR-0007 §4、テスト仕様 EXT-04 |
| 延長の境界 | `終了時刻 − 5分 ≦ 受付時刻 ＜ 終了時刻` で延長（ちょうど5分前は延長する。EXT-02） | テスト仕様 EXT-01・02 |
| 即決と最低入札額 | 即決価格以上の入札は、最低入札額に足りなくても即決にする（例：現在の価格 2,950円・最低 3,050円でも、即決価格 3,000円の入札は落札） | 「即決価格以上で入札すると落札」（ADR-0007 §5） |
| 時刻 | ロック取得後の API サーバーの時刻を、DB 基準の時刻とみなす | サーバー1台・SQLite3 の間は同じ。PostgreSQL 移行時に DB の時刻を使うか見直す |
| 冪等性の記録 | 成功だけでなく、業務上の拒否（`BID_TOO_LOW`・`AUCTION_NOT_ACTIVE`・`SELLER_CANNOT_BID`・`BID_LIMIT_EXCEEDED`）も保存し、同じキーの再送には同じ応答を返す（IDEM-04）。キーの範囲は「会員・オークション」ごと | トランザクション設計 4章 |
| 冪等性の記録の保存期間 | まだ削除しない | トランザクション設計 11章で未決 |
| 取引（Order） | 即決のとき、同じトランザクションで作る（状態 `awaiting_payment`、商品情報・配送条件のスナップショットつき）。手数料（ADR-0009）は提案中のため、まだ持たない | 仕様書 5.7 |

## まだないもの

- 公開の入札履歴 `GET /api/v1/listings/{id}/bids`（匿名化の方針が未決）
- 自分の入札一覧（マイページ、USR-001）
- 通常の終了・早期終了による落札（AUC-001）
- 入札の通知（Outbox、NTF）
