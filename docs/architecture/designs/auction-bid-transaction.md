# 入札・終了処理のトランザクション仕様

- 状態: 提案（DB実装前の論理仕様）
- 対象: MVPの通常オークション
- 関連: [オークション業務ルール](../../product/auction-rules.md)、[ADR-0004](../adr/0004-auction-operating-rules.md)、[ADR-0006](../adr/0006-database-sqlite-to-postgresql.md)、[API設計案](../../api/openapi.md)、[ドメインモデル](../domain-model.md)

## 1. 目的と適用範囲

この文書は、同時入札、入札と終了処理の競合、再送による二重登録を防ぐためのDB書込み契約を定める。SQLAlchemy等のORMやDB製品に依存しない論理仕様とし、SQLite3とPostgreSQLでロック取得方法が異なる点はADR-0006の抽象化境界に従う。

## 2. 整合性不変条件

1. 受付済み入札は、認証・権限・オークション状態・終了時刻・最低額の検証をすべて通過したものだけとする。
2. 1オークションの入札受付は全て直列化し、後続入札は先行入札の確定後の価格で再検証する。
3. `current_price`、`highest_bidder`、`bid_count`等の集計値を保持する場合、受付済みBid履歴と同一トランザクションで更新する。履歴を正とし、集計値は履歴と矛盾させない。
4. 1回の入札要求につき、同一ユーザー・同一オークション・同一冪等性キーで受け付けるBidは最大1件。
5. 終了確定後の入札は受け付けない。終了確定と入札受付のどちらが先にロックを得ても、この条件を守る。
6. 受付済みBidは通常更新・削除しない。訂正・運営対応は別の監査可能な操作として記録する。
7. 通知やメール送信の成否は、入札・落札確定のコミット結果を変更しない。

## 3. 入札の処理手順

### 3.1 トランザクション前

- セッションから会員IDを得る。リクエストのユーザーIDは採用しない。
- 金額が正の整数JPYで上限以下、冪等性キーが形式・長さ制限内であることを検証する。
- 認証失敗、形式不正等、DB状態に依存しないエラーはトランザクション開始前に返してよい。

### 3.2 ロック取得後の処理

オークションを特定し、書込みトランザクションを開始する。入札・出品変更・停止・終了処理は、同一対象について同じオークション受付ロックを共有する。複数行をロックする場合は常に `Auction -> Listing -> Bid/Order/Idempotency` の順に取得し、デッドロックを避ける。

以下を一つのトランザクション内でこの順に行う。

1. 対象Auctionの受付ロックを取得する。PostgreSQLではAuction行ロック、SQLite3ではADR-0006に定める書込み予約トランザクション等を使う。
2. 同じユーザー・オークション・冪等性キーの記録を検索する。既存なら、リクエスト本文ハッシュが一致する場合は保存済み結果を返し、異なる場合は `IDEMPOTENCY_KEY_REUSED` を返す。既存処理中なら完了を待って結果を返す。
3. DB基準の現在時刻を取得する。ロック待ち時間を含め、ロック取得後に判定する。
4. Listing/Auctionが公開・開催中であること、利用者が停止されていないこと、出品者本人でないことを確認する。
5. `now < ends_at` を確認する。等しい場合も終了後として拒否する。
6. ロック下の最新受付済みBidから現在価格・最高入札者を決め、初回は開始価格以上、以降は現在価格と価格帯別増分による最低額以上であることを確認する。
7. 受付順を確定する値（単調増加するBid IDまたはオークション内連番）と受付時刻を割り当て、Bidを追記する。
8. Auctionの集計列を持つ場合は同じトランザクションで更新する。冪等性キーとリクエストハッシュ、成功レスポンスを保存する。
9. 通知が必要ならOutboxイベントを同じトランザクションに追加する。
10. コミット後に受付成功レスポンスを返す。

DBがトランザクションをロールバックした場合、Bid、集計値、冪等性結果、Outboxのいずれも確定してはならない。

### 3.3 受付順

受付順はクライアント送信時刻やAPIサーバー到着時刻ではなく、オークションロック取得後に直列化されたDB処理順で決める。`accepted_at` が同値でも曖昧にならないよう、最高入札者の決定には受付連番または一意なBid IDによる確定順を使う。連番を割り当てた後にトランザクションが失敗し欠番が生じても問題ない。

## 4. 冪等性契約

- キーのスコープは `(auction_id, user_id, idempotency_key)` とし、DB一意制約で重複処理を防ぐ。
- 同一キー・同一リクエストの再送は、初回処理結果（成功または確定した業務拒否）を返し、Bidを追加しない。
- 同一キーを異なる金額等の内容で再利用した場合は `IDEMPOTENCY_KEY_REUSED` とする。
- キー記録と成功Bidは原子的に確定する。期限切れキーを再利用可能にする場合の保持期間はAPI契約で別途決める。保持期間が未決の間はキーを削除・再利用しない。
- タイムアウトでコミット成否が不明なクライアントは、同一キー・同一本文で再送する。新しいキーで再送してはならない。
- DB障害等の一時エラーは結果確定として記録せずロールバックし、同じキーで再試行可能とする。

業務拒否を冪等性結果として固定する場合は、拒否理由と返却内容もキー記録に保存する。終了後・価格更新後に同じ要求を再評価して別結果にしない。

## 5. 終了処理との競合

終了ワーカーは候補検索後、対象Auctionの受付ロックを取得し、ロック取得後のDB時刻と状態を再確認する。

- `now < ends_at` ならまだ終了確定しない。
- `now >= ends_at` なら状態を終了へ遷移し、ロック下で最高入札を確定する。
- 落札ありの場合、Orderを作成する。入札なしの場合は落札者なしで終了する。
- Auction終了状態、Order、Outbox通知イベントは同じトランザクションで確定する。
- `Order.auction_id` に一意制約を設け、ジョブの重複実行や複数ワーカーでも注文を二重作成しない。
- 終了処理と入札が競合した場合、ロックを先に取得した処理が先行する。終了時刻前にロックを取得した入札でも、時刻判定時点が `ends_at` 以降なら拒否する。
- Order作成やコミットに失敗した場合、終了状態も確定させず、処理全体を再試行可能にする。

## 6. 出品変更・運営停止との競合

公開出品の編集、出品者の取り下げ、運営停止・解除も同じAuction受付ロックを取得してから状態とBid件数を確認する。これにより「入札がないことを確認して取り下げる」処理と同時の入札を直列化する。入札が先に確定すれば入札後の編集・出品者取り下げを拒否し、取り下げ・停止が先に確定すれば後続入札を拒否する。

## 7. 制約とデータ記録

少なくとも次のDB制約を設ける。具体的な型・DDLはスキーマ設計で定める。

- `Bid.amount_yen > 0`、AuctionとUserへの外部キー。
- `(auction_id, user_id, idempotency_key)` の一意制約（キーをBidに直接持たせない場合は専用冪等性テーブルに設定）。
- `Order.auction_id` の一意制約。
- Auctionの状態・価格・時刻に対するCHECK制約（DB間で表現できる範囲）。
- Bidは受付済み履歴として追記し、訂正履歴を別途監査可能にする。

入札成功の記録には、Auction、入札者、金額、受付時刻、受付順、冪等性キーの識別情報を結び付ける。キー原文や認証トークンをログへ出さない。監査ログ・Outboxの個人情報は必要最小限にする。

## 8. エラー・再試行

| 状況 | DB処理 | API上の扱い |
|---|---|---|
| 最低額未満、終了、自己入札、停止中 | Bidを作らない。業務拒否結果は冪等性記録に固定 | 理由と、該当時は最新最低額を返す |
| 同一キーの再送 | 既存記録を返し、再書込みしない | 初回と同じ結果 |
| デッドロック/ロック競合 | トランザクション全体をロールバック | 内部で回数・上限を定めて再試行。超過時は再試行可能エラー |
| DB接続断・コミット結果不明 | 成否を推測しない | クライアントは同一キーで再送 |
| 永続的な整合性違反 | 全体をロールバックし、詳細を利用者に漏らさない | 一般エラー。運用ログに相関ID |

ロック待ち・トランザクション時間には上限を設け、長時間ロックを保持したまま外部API、メール、画像処理を呼び出さない。再試行回数・待機方式・タイムアウト値は負荷と採用DBに基づき実装時に決定する。

## 9. 通知と外部処理

メール、プッシュ通知、分析イベント等の外部処理を入札・終了トランザクション中に実行しない。Outbox行だけを同時コミットし、別ワーカーが送信する。Outboxイベントには一意なイベントIDを付け、送信側も重複処理できるようにする。通知送信失敗は再試行し、入札・落札のDB状態を戻さない。

## 10. 必須の検証シナリオ

- 同時に複数入札し、最低額再検証・受付順・最高入札者・入札数が一貫する。
- 同一キーの並行送信、タイムアウト後の再送、同一キー別本文を検証する。
- 入札と終了処理、入札と出品取り下げ、入札と運営停止を競合させる。
- 終了時刻直前・一致・直後をDB時刻で検証する。
- 各書込み段階で障害を注入し、部分的なBid・集計値・Order・Outboxが残らないことを検証する。
- 終了ワーカーを複数回・並行実行し、Orderが最大1件であることを検証する。
- 本番採用DB（PostgreSQL）上でロックとトランザクションの統合テストを実施する。SQLiteのテストだけで行ロック挙動を保証したことにしない。

## 11. 未決・実装時に固定する項目

- 冪等性キーの最大長、形式、保存期間
- ロックタイムアウト、デッドロック再試行回数、APIタイムアウト
- Auction集計列を保持するか、都度履歴から算出するか
- Outboxのスキーマ、配信保証、保持・削除期間
- 公開入札履歴の匿名表示と履歴ページング
- ORM、DB分離レベル、マイグレーションDDL

これらは本論理仕様の不変条件を弱めない形で、DB・API実装の採用ADRまたは設計詳細に記録する。
