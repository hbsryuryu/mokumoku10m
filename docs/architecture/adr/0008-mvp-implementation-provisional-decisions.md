# ADR-0008: 出品・入札・落札の実装を始めるための仮決め

- 状態: 採用（**仮決め**。実装しながら見直す）
- 日付: 2026-11-13
- 決定者: hbsryuryu（チームでの確認は PR で行う）
- 関連: [ADR-0004](0004-auction-operating-rules.md)（出品の編集・取り下げ）、[ADR-0005](0005-google-only-authentication.md)（Google 認証）、[ADR-0006](0006-database-sqlite-to-postgresql.md)（DB）、[ADR-0007](0007-align-with-yahoo-auctions.md)（Yahoo!オークション準拠）、[`auction-site-spec.md`](../../product/auction-site-spec.md)、[`roadmap.md`](../../product/roadmap.md)

## 背景

ロードマップのフェーズ2（出品）・フェーズ3（入札・終了）のバックエンド API を書き始めたい。入札・終了のルールとトランザクション設計は揃っているが、次の3点が決まっておらず、コーディングが止まる。

1. ログイン（AUTH-001）が未実装で、出品・入札に必要な「ログイン済みの会員」を作れない
2. 出品の入力項目の細部（文字数の上限、カテゴリ、商品状態、配送条件、画像）が「未決」
3. 開催期間の開始時刻、価格の上限、終了処理の動かし方が決まっていない

これらを**仮の値**で決め、実装しながら見直す。

## 決定

### 1. 開発用ログイン（AUTH-002）

**ログイン方式は Google のみ（ADR-0005）のまま変えない。** Google ログイン（AUTH-001）を実装するまでの間、手元の PC で出品・入札を試すための開発専用の仕組みを用意する。

- `POST /api/v1/dev/login`（表示名を指定）で、開発用の会員を作成または取得し、**Google ログインと同じアプリのセッション**を発行する。出品・入札などのコードは、ログイン方式を意識しない。
- 開発用の会員は `AuthIdentity.provider = 'dev'` で記録する（Google の会員は `'google'`）。
- **安全策**
  - `APP_ENV=local` かつ `DEV_LOGIN_ENABLED=true` のときだけ、このエンドポイントを登録する。それ以外では存在しない（404）。
  - `APP_ENV` が `local` 以外なのに `DEV_LOGIN_ENABLED=true` の場合、**アプリは起動を拒否する**。
  - staging / production の DB に `provider = 'dev'` の記録があってはならない（移行時・公開前の確認項目にする）。
- Google ログイン（AUTH-001）を実装したあとも、自動テストとローカル開発のために残す。

### 2. 出品の入力項目（LST-004）

現在の静的デモの値をそのまま仮の値にする。Yahoo!オークションの値に合わせるかは、要件を書くときに公式ヘルプで確認して見直す（ADR-0007）。

| 項目 | 仮の値 |
|---|---|
| タイトル | 必須、1〜60文字。前後の空白を除く |
| 説明 | 必須、1〜500文字。プレーンテキストのみ（HTML は使えない。表示時にエスケープ） |
| カテゴリ | 必須。階層なしの5種類：ファッション、インテリア、本・ホビー、家電、その他。マイグレーションで初期データとして入れる（管理画面での追加は LST-002 で検討） |
| 商品状態 | 必須。4種類：新品・未使用、目立った傷や汚れなし、やや傷や汚れあり、傷や汚れあり |
| 配送条件 | 必須。送料負担（出品者／落札者）と、配送方法の説明（1〜80文字） |
| 画像 | **最初の実装では扱わない**。公開時の必須チェックにも入れない。LST-003 で追加する |

### 3. 価格と開催期間（LST-004・BID-001）

| 項目 | 仮の値 |
|---|---|
| 開始価格 | 必須。1円〜1,000万円の整数 |
| 即決価格 | 任意。開始価格より高く、1,000万円以下の整数 |
| 入札額（最高入札額）の上限 | 1,000万円 |
| 開始時刻 | **公開と同時に開始**する（開始時刻の予約は MVP では扱わない）。下書き中は開始しない |
| 終了日時 | 公開時刻から13時間後〜7日11時間後、1時間単位（ADR-0007） |
| 自動延長 | 「あり／なし」、既定値は「あり」（ADR-0007） |

### 4. 終了処理（AUC-001）

- 終了処理は、**API サーバーと同じプロセスの中で定期的に実行する**（例：30秒ごと）。ADR-0006 の「SQLite3 の間はワーカーを API と同じプロセスで動かす」に合わせる。
- 同じ処理を手動でも実行できるようにする（テストと復旧のため）。
- 判定はトランザクション設計（`auction-bid-transaction.md` 5章）のとおり、ロック取得後の DB 時刻と最新の `ends_at` で行う。
- 落札した場合は `Order`（状態 `awaiting_payment`）を作成するところまでとする。支払い・発送・評価はフェーズ4。

### 5. 機能ID

| ID | 機能 | 範囲 |
|---|---|---|
| AUTH-002 | 開発用ログイン | 上の1 |
| LST-004 | 出品 | 下書き作成・編集・公開・取り下げ、公開中の一覧・詳細 |
| BID-001 | 入札 | 自動入札による価格計算、入札単位、自動延長、即決、最高入札額の引き上げ、入札履歴 |
| AUC-001 | 終了・落札 | 定期的な終了処理、早期終了、`Order` の作成 |

## 理由

- 仮の値でも、実装・テスト・レビューを回し始めるほうが、学習目的のチームにとって得るものが大きい。値は設定やマイグレーションで後から変えられる。
- 開発用ログインを「同じセッションを発行する別の入口」にすることで、Google ログインの実装を待たずに、出品・入札のコードを本番と同じ形で書ける。
- 画像と開始時刻の予約を後回しにすることで、最初の実装の範囲を「出品→入札→落札」の流れに絞れる。

## 影響

- `auction-site-spec.md` の「未決」の一部（タイトル・説明の上限、カテゴリ、商品状態、最短・最長期間）は、本 ADR の仮の値を参照する。
- 画像は MVP の要件のまま残る。LST-003 で追加するまで、公開時の必須チェックに入れない。
- `.env.example` に `APP_ENV` と `DEV_LOGIN_ENABLED` を追加する（コードの PR で行う）。

## 見直す条件

- 各機能の要件を書くとき、Yahoo!オークションの公式ヘルプと比べて大きく違う値があったとき
- Google ログイン（AUTH-001）を実装したとき（開発用ログインの安全策を再確認する）
- PostgreSQL に移行するとき（終了処理を別のワーカープロセスに分けるか検討する）
