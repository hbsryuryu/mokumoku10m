# ADR-0010: Web フロントエンドは Next.js で作る

- 状態: 採用（スタイリング・型の生成ツールなどの細部は、最初の実装の PR で決める）
- 階層: L2 決定（技術）
- 上位: [ADR-0003](0003-production-stack-pending.md)
- 関連: [ADR-0001](0001-backend-framework.md)（FastAPI）、[ADR-0002](0002-prototype-scope.md)（静的デモ）、[ADR-0005](0005-google-only-authentication.md)（Google 認証）、[ADR-0007](0007-align-with-yahoo-auctions.md)（Yahoo!オークション準拠）
- 日付: 2026-11-13
- 決定者: hbsryuryu（チームでの確認は PR で行う）

## 背景

バックエンド API（FastAPI）は、ログイン（開発用）と出品まで動くようになった。一方、利用者向けの画面はまだない。

- 静的デモ（`index.html` / `app.js`）は見た目の確認用で、API とつながっておらず、入札ルールも古い（ADR-0002）。
- FastAPI の `/docs` は開発者向けの確認画面で、利用者向けではない。
- AGENTS.md・`docs/architecture/overview.md` では、フロントエンドの初期候補を「Next.js + TypeScript」としていたが、ADR-0003 で「Web は未決」のままだった。

## 選択肢

1. **Next.js + TypeScript**
   - 長所：AGENTS.md の初期候補どおり。商品一覧・詳細をサーバー側で HTML にでき、検索エンジンに載りやすい（仕様書 9.2）。ページが増えても構成を保ちやすい。FastAPI の OpenAPI から TypeScript の型を生成できる。情報が多く学習しやすい。
   - 短所：覚えることが多い（React、サーバー／クライアントの区別）。Python とは別に Node.js の環境が要る。
2. **今の静的デモ（HTML + JavaScript）を API につなぐ**
   - 長所：すぐ動く。今のデザインを活かせる。
   - 短所：画面が増えると管理が難しい。型の共有がない。いずれ作り直しになる可能性が高い。
3. **React + Vite（ブラウザだけで動く SPA）**
   - 長所：Next.js より仕組みが単純。
   - 短所：商品ページを検索エンジンに載せにくい。ルーティングなどを自分で組む必要がある。
4. **FastAPI のテンプレート（Jinja2）でサーバー側で HTML を作る**
   - 長所：Python だけで完結する。
   - 短所：入札のような動きのある画面が作りにくい。フロントエンドの学習にならない。

## 決定

**選択肢1（Next.js + TypeScript）を採用する。**

| 項目 | 決定 |
|---|---|
| 置き場所 | `apps/web/`（AGENTS.md の構成例どおり。API は `apps/api/`） |
| 言語 | TypeScript |
| バージョン | 導入時点の安定版を使い、`package.json` とロックファイルで固定する。Node.js は LTS 版 |
| ページの作り方 | 商品一覧・詳細など公開ページは、サーバー側で HTML を作る（検索エンジン・表示速度のため）。入札フォームなど動きのある部分だけをブラウザ側の処理にする |
| API との通信 | **ブラウザからは同じオリジンに見せる。** Next.js の転送（rewrites）で `/api/*` を FastAPI に送る。こうすると、ログインの Cookie（`HttpOnly`・`SameSite=Lax`）がそのまま使え、CORS の設定が要らない。本番でも、同じドメインの下で Web と API を配信する |
| 認証 | ログイン状態の判定は FastAPI のセッション（`/api/v1/me`）に任せる。Next.js 側で独自のログインやトークンを持たない（ADR-0005）。サーバー側で会員ごとのページを作るときは、受け取った Cookie を API に渡す |
| ローカル開発 | `compose.yaml` に `web` サービスを追加し、`docker compose up` で API と一緒に起動できるようにする（最初の実装の PR で行う） |
| デザイン | 静的デモのデザインを参考にする。Yahoo!オークションの画面・文章・画像は使わない（ADR-0007） |

**最初の実装の PR で決めること**（L3 の仮決めか、この ADR への追記で記録する）

- スタイリングの方法（候補: Tailwind CSS。AGENTS.md の初期候補）
- OpenAPI から TypeScript の型を作るツール（候補: openapi-typescript）
- テストの道具（単体テスト・E2E）と、Lint・型チェックの設定

## 理由

- 商品一覧・詳細は誰でも見られるページで、検索エンジンに載ることが集客に直結する。サーバー側で HTML を作れる Next.js が向いている。
- 同じオリジンに見せる構成にすると、FastAPI で作ったセッションの仕組み（Cookie）を変えずに使える。CORS や Cookie の設定ミスによる不具合・脆弱性を避けられる。
- AGENTS.md の初期候補どおりで、チームの学習テーマ（モダンなフロントエンド）にも合う。

## 影響

- **Hono（ADR-0001 のサブ候補）との関係**：Next.js は API の転送だけを行い、業務ロジックは持たない。BFF（フロント用の中継サーバー）が必要になったら、そのときに Next.js で作るか Hono を使うかを別の ADR で決める。
- **静的デモ（ADR-0002）**：Next.js の画面が出品・検索・入札をカバーしたら、静的デモは役目を終える。削除するかは、そのときに決める。
- **開発環境**：Node.js が必要になる（Docker で動かす場合は不要）。
- **文書**：`docs/architecture/overview.md` と ADR-0003 の「Web は未決」を更新した。
- **順番**：入札・終了処理の API（BID-001・AUC-001）を先に完成させてから、画面の実装に入る（API の形が固まってからのほうが作り直しが少ない）。

## 見直す条件

- Next.js の学習・運用の負担が大きすぎて、MVP の進みが止まったとき（選択肢2・3に戻すかを検討する）
- 本番の配信環境（ADR-0003 のクラウド選定）が、Next.js のサーバー側の処理に向かないと分かったとき
